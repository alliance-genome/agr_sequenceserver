# Audit, October 2026

A sweep of all three repos -- the web app, the database build pipeline and the
config -- plus the data and containers actually deployed on the host. Six
auditors worked a dimension each; every finding then went to a second agent
whose instructions were to *refute* it, and only what survived is recorded here.

74 findings survived: 17 high, 30 medium, 27 low. This document is the triage,
not the raw list; the full list is the appendix at the end.

Two things about the method are worth knowing before trusting any single line
of it.

**The verifier was wrong in both directions.** It confirmed two findings that
are false, and refuted one that is real. The two false ones came from a stale
checkout -- `/home/ec2-user/gitroot/agr_blastdb_manager` was six commits behind
`main` while the audit ran, so claims that the index writer cannot produce
WormBase or FlyBase symbols, and that nothing writes `.names.display.json`, were
describing code that had been superseded. Both are false against `main`. The
refuted-but-real one is the ZFIN `>` bug (fixed, PR #73): reproducing it takes
two lines. The lesson is narrow and practical -- the findings that most need
checking by hand are the ones touching code written in the same session.

**"Confirmed" means a defect was demonstrated, not that it matters.** Severity
here is the auditors' and has not been re-weighted against the Alliance's own
priorities. A `low` that annoys a curator daily may matter more than a `high`
nobody can reach.

## Fixed in this pass

### Three ways a request reached the filesystem or the CPU

PR [#31](https://github.com/alliance-genome/agr_sequenceserver/pull/31). All
three were reproduced on a live instance before and after. Two are upstream
SequenceServer's, not this fork's, and all three were live on test, dev and
prod.

The job id was taken from the request and became a path. `Job#initialize` did
`params.fetch(:id, SecureRandom.uuid)` on the search form's params, and
`Job.validate` checks method, sequence, databases and options but never `:id`.
Because `dir` is `File.join(DOTDIR, id)`, a submitted id could place the job
directory anywhere the process could write, as root in the container. It was
also an arbitrary delete: `mkdir_p` against an existing file raises `EEXIST`,
which falls past the `ENOSPC` and `EACCES` clauses into `rescue StandardError`,
whose first act is `rm_rf dir`. Since `/var/sequenceserver-data` is mounted
read-write into all three containers, that reached the BLAST databases every
deployment shares.

The four static-asset routes joined the URL splat onto `public/`. Mustermann
percent-decodes that capture after the server has normalised the path, so an
encoded separator survived normalisation and then acted as one: the Gemfile,
the application source and `conf/*.conf` were all retrievable unauthenticated,
with no application log entry. They now share one helper that resolves the path
and requires it to remain inside its directory.

`?query=` forked `blastdbcmd` once per database per comma-separated id, with no
cap and no budget. A miss costs one fork per database, and SGD's fungal set has
312 of them. 100 ids measured ~31,000 process spawns and about 26 minutes of
one worker. It is now capped at 10 ids with the same 15-second budget the
`?name=` path beside it already had; 100 ids now costs 15.2 seconds.

### Everything else fixed here

`POST /cloud_share` is gone, with its component, both specs, the dead state and
props in `report.js`, and `rest-client`. It was CSRF-exempt, unreachable since
the Share-results panel was removed, and could not be switched off: the guard
tests truthiness while the documented value is the string `'disabled'`, and it
did not `halt` in any case, so an unfinished job was relayed to a third party
regardless.

The gene search box was a `<form>` nested inside `<form id="blast">`. A nested
form is discarded by the parser, so pressing Enter in the gene box submitted
the BLAST search.

Gene search offered candidates from the 762 deployed databases built without
`-parse_seqids`, where `blastdbcmd` returns the synthetic ordinal
`BL_ORD_ID:0` in place of an accession and the backfill wrote those into the
indexes. On ZFIN that meant 50 rows all reading `BL_ORD_ID:0`, every one dead
on click. They are skipped now, so the box is honestly empty there.
`VALID_SEQUENCE_ID` cannot be used for the check: it permits `:` and accepts
`BL_ORD_ID:0` quite happily.

The no-results hint told users to try the symbol rather than the full name.
True when only deflines were indexed, wrong since the FlyBase synonym table was
joined in -- which is the change that made `white` searchable in the first
place.

CI had never run. The workflow triggers on `master`, this fork's default branch
is `main`, and no `master` exists on origin. Pointing it at `main` immediately
surfaced why that went unnoticed: `bundle exec rspec` cannot run at all,
because the fork gave `BLAST::Report#initialize` a required `env_config` and
never updated the ten spec files that construct a report directly. `env_config`
now defaults to `[]`, which is already what `routes.rb` passes for a release
with no `environment.json`.

The build path and the backfill derived different names for the same ZFIN
database (PR [agr_blastdb_manager#73](https://github.com/alliance-genome/agr_blastdb_manager/pull/73)).
`build_name_index` passed the raw FASTA line with its `>` attached, and the
ZFIN pattern is `\A`-anchored because a ZFIN defline leads with its symbol. The
deployed ZFIN indexes came from the backfill and are correct, so this was
latent -- but a rebuild would have silently replaced them with accession-only
ones.

## The test suite, now that it runs

Turning CI on produced the first reading of these suites in the life of the
fork, and it took two fixes to get one. The workflow triggered on `master`
while the default branch is `main`, so nothing had ever run; pointing it at
`main` then failed in 40 seconds on a CodeClimate reporter download that now
answers 404, before reaching a test. With coverage made best-effort, the
pipeline runs end to end.

What it reports:

| | rspec | jest |
|---|---|---|
| `73e4a38a` (before #31) | **0 examples**, 10 errors outside examples | 1 failed, 29 passed |
| `b435058e` + #32 | 367 examples, **66 failures** | 1 failed, 29 passed |

The 66 are newly *visible*, not newly *caused*. Before, `bundle exec rspec`
could not collect an example at all: this fork gave `BLAST::Report#initialize`
a required `env_config` and never updated the ten spec files that construct a
report directly. Defaulting it to `[]` -- which is already what `routes.rb`
passes for a release with no `environment.json` -- lets the suite load.

**The dominant cause of the 66 is that nothing populates `Database.collection`
outside a request.** `init_database` is defined at `lib/sequenceserver.rb:191`
and called from nowhere; line 204 inside it holds the only
`Database.collection = makeblastdb.formatted_fastas` that is not in a route.
This fork moved database loading into the request path -- six call sites in
`routes.rb` -- which is right for the concurrency fix and leaves every unit
spec that expects `Database.first` or `Database.all` to be populated looking at
an empty hash. `spec/database_spec.rb` fails exactly that way:
`.retrieve` returns `# ERROR: SI2.2.0_06267 not found in any database`, and
`#include?` fails alongside it.

That is a test-architecture problem rather than a product defect, and the fix
is a decision rather than a patch: either `spec_helper` populates the
collection the way a request does, or `init_database` is called again and the
per-request assignment becomes a refinement of it rather than the only source.
It should not be guessed at.

Two things are worth stating about the attribution, because the obvious
suspicion is that the hardening commit caused this. It did not, and the
evidence is specific: #31's whole change to `database.rb` is a cap that does
nothing at one id and a deadline that emits a *different* message
("gave up after 15s"), and it does not touch `#include?` at all, which fails
the same way. The isolating run -- `73e4a38a` plus only the `env_config`
default -- could not be obtained, because GitHub stopped creating Actions runs
for this repository partway through the investigation. So the attribution rests
on reading the diff rather than on a measurement, and is recorded here as such.

## Not fixed, and what I would do about it

### The data is wrong in places, and that needs the MODs

These are the findings I would act on first, because they are wrong *answers*
rather than wrong code, and a curator cannot tell.

**ZFIN's "TALEN Sequences" database contains morpholinos.** Two entries in
`conf/ZFIN/databases.ZFIN.production.json` carry the identical `blast_title`,
so they collide on one output directory and the morpholino set is what is
actually served under the TALEN label. The real TALEN data is absent from the
deployment entirely. Nothing in the pipeline detects a title collision, which
is the more general problem: WS285 collapses three C. elegans bioprojects the
same way.

**ZFIN serves no protein databases at all**, on prod or on test. "Published
Zebrafish Proteins" is declared `seqtype nucl` and its source archive is an
empty gzip, so the build left an empty directory and no database.

**ZFIN's "mirRNA Mature" contains stem-loop hairpins**, because the entry
points at the stem-loop FASTA; the entry that should hold the stem loops points
at a misspelled URL that 404s. Three ZFIN URIs 404 in total.

**FlyBase gene-level links can never resolve.** Every FB config since
FB2025_01 sets `genome_browser.data_url` to an S3 prefix that does not exist,
and `gene_track` is `"Curated Genes"` -- a WormBase track name, with a space in
it that breaks the shell command the consumer builds.

All of these want a conversation with the MOD rather than a patch from us, and
FlyBase is already mid-conversation about the transcript file.

### The config repo validates almost nothing

`conf/global.yaml` has been stuck at FB2024_04 since the FlyBase update
workflow started excluding it from its own PR. The validator and the pre-commit
hook only check the six files `global.yaml` names, so 27 of 33 configs -- every
file actually deployed -- are never validated. Four WB configs with a
`metaData` typo merged CI-green through that gap. Separately, the schema marks
three `genome_browser` fields required that the consumer treats as optional,
and its provider enum omits RGD, which is live with two committed configs; so
registering RGD would make CI fail on correct config.

This is a contained piece of work and the highest-leverage thing in the config
repo: fix `global.yaml`, make the validator walk `conf/**` rather than the
manifest, then fix what that surfaces.

### Pipeline hazards that will eventually cost a release

`copy_to_production` `rmtree`s the live databases directory before copying, and
the driver triggers it whenever a single entry succeeded -- so a narrow or
partial run deletes live databases the staging tree no longer holds, with no
atomicity and no rollback. `run_makeblastdb` likewise `rmtree`s its whole output
directory on failure, and two config entries can legitimately share one, so one
entry's failure deletes another's finished database. And the pipeline prints
"PIPELINE COMPLETED SUCCESSFULLY" and exits 0 regardless of how many entries
failed, because `process_files` discards the return value.

The exit code is a one-line fix and should happen immediately: every other
hazard here is one a green run currently hides.

### Deployment and housekeeping

Prod is four merged PRs behind and carries all three of the request-handling
defects above. It needs only an image rebuild, since the data is shared. One
thing to know first: job results live in the container's writable layer, so
recreating the container 404s every outstanding result URL -- about 1,241 jobs
and 3.5 GB there now, growing ~1.5 GB a day against 80 GB free.

Three WormBase releases were retired by renaming them with a leading dot, and
all three instances still serve them, because the version pattern permits a
leading dot. The eight FlyBase releases on disk hold 37.5 GiB of byte-identical
duplicates -- the non-Drosophila outgroups, which do not change between
releases.

Every HTML page render makes a synchronous, uncached, un-timed-out HTTPS call
to `alliancegenome.org` for the asset manifest, which ties this service's page
load to an external host.

### Known and unchanged

ZFIN and RGD carry no gene symbols in their deflines, so gene search cannot
answer for them; the `BL_ORD_ID` fix means the box is now honestly empty there
rather than full of dead rows. The ALLIANCE-wide deployment still serves one
database instead of the full set -- see `docs/ALLIANCE_WIDE_PLAN.md`. The
FlyBase transcript file is still a six-way concatenation with four files
doubled; `/home/ec2-user/fb-transcript-6.69-check/` watches both it and the
canonical export.
